# Code Complexity & Health Metrics

This document defines Catan's complexity measures, thresholds, and generated-evidence ownership. Current measurements are generated by Dependency Maritime and committed under [`.maritime/`](../.maritime/); this guide does not duplicate a point-in-time health report.

---

## 📊 Complexity Dimensions & Warning Thresholds

The Maritime bundle evaluates production TypeScript source files in `src/` across four dimensions:

| Dimension | Metric | Warning Threshold | Description |
| :--- | :--- | :--- | :--- |
| **Length** | **LOC** (Lines of Code) | > 300 LOC | Total lines in a measured source file. |
| **Coupling** | **Fan-Out** (Dependencies) | > 15 Imports | Number of dependencies reported for the measured module. |
| **Stability** | **Instability (I)** | 0.30 – 0.70 | $I = \frac{\text{Fan-Out}}{\text{Fan-In} + \text{Fan-Out}}$. Modules in this range may change for many reasons while also affecting many dependents. |
| **Logic** | **Cyclomatic Complexity** | > 10 | Maximum cyclomatic complexity reported by ESLint for the file. |

The current health score and hotspot tables live in [`.maritime/complexity-report.md`](../.maritime/complexity-report.md). Machine-readable per-file values live in [`.maritime/complexity-metrics.json`](../.maritime/complexity-metrics.json).

## 🛠️ Canonical Maritime Evidence

The tracked [`.maritime/`](../.maritime/) directory is the authoritative generated bundle:

- [`complexity-metrics.json`](../.maritime/complexity-metrics.json) — machine-readable per-file metrics.
- [`complexity-report.md`](../.maritime/complexity-report.md) — human-readable health and hotspot report.
- [`dependency-graph.json`](../.maritime/dependency-graph.json) — canonical machine-readable structural evidence.
- [`manifest.json`](../.maritime/manifest.json) — versioned bundle manifest and validation envelope.

[`docs/images/dependency-graph.svg`](./images/dependency-graph.svg) is derived presentation generated from that same canonical graph by Maritime's renderer. It is not a second source of structural truth and must not be hand-edited.

### Evidence profile vs. enforcement profile

Catan intentionally uses two Dependency-Cruiser entry points with one policy source:

- `config/dependency-cruiser.cjs` is the full architecture-enforcement configuration used by `npm run check:arch` and `npm run build`.
- `config/dependency-cruiser.maritime.cjs` reuses that exact policy but excludes test/spec helpers from the committed Maritime evidence graph. Tests remain covered by the normal test suite and full architecture check; the evidence profile simply keeps production coupling and the deterministic Graphviz presentation bounded and readable.

This separation must not be used to weaken architectural rules. Any forbidden-dependency rule belongs in `config/dependency-cruiser.cjs` so both profiles inherit it.

## 🔄 Regeneration contract

The **Generated Artifacts** workflow is the single PR-branch writer for `.maritime/*` and `docs/images/dependency-graph.svg`. It runs the pinned Maritime Action and CLI, validates that the bundle contains measured production files and a non-empty graph, then commits the evidence and SVG together when substantive output changes.

Do not hand-edit generated evidence. For local reproduction and exact pinned commands, follow [DEVELOPMENT.md](./DEVELOPMENT.md).
